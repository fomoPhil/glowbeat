# Party Mode v1.1 addendum (from Phil's first hardware session, 2026-09-11)

Extends the v1 spec. Everything here was approved by Phil after testing Party Mode on his six H6004 bulbs.

## 1. Auto-gain (already patched, needs tests and review)
`App/Model/AutoGain.swift` rescales every audio frame against a slowly decaying per-band and RMS peak (decay 0.9965 per frame at 50 fps, floor 0.01) before the beat detector and the level meter see it. Result: the level bar fills at any playback volume and normal kicks register as beats. Keep the design; add unit tests (loud then quiet track both reach ~1.0; silence stays at 0; floor prevents amplifying hiss; reset).

## 2. Gate marker on the Level bar
- A draggable marker on the Level bar in the Party panel (and a matching value in Settings), range 0 to 1, default 0.15. Persisted in GlowbeatSettings as `partyGate`.
- Semantics: the engine computes a smoothed loudness `L` (auto-gained RMS, attack fast, release ~300 ms). While `L < gate`, the effect output for every bulb is the palette dim base and no beats are forwarded to the effect. While `L >= gate`, everything works as today. Hysteresis: open at `gate`, close at `gate * 0.8`, so a level hovering at the threshold does not flicker.
- Below the gate the bulbs sit at the dim base (never fully off).
- UI: the marker is a small triangle or line on the meter; drag horizontally; show the value as a percentage on hover or while dragging; accessibility label "Party gate".

## 3. Glow effect (volume driven)
- Fourth `EffectKind` case `.glow`, display name "Glow", summary "Louder is brighter. Color drifts through the palette."
- All bulbs same color. Brightness follows `L` (auto-gained RMS via the frame's rms) mapped through the gate: `b = clamp((L - gate) / (1 - gate))` with attack ~50 ms and release ~400 ms so it breathes rather than flickers. Color: the palette colors cross-faded slowly, one color per ~8 s, independent of beats. Output = dimBase blended toward the current palette color by `b`.
- Uses `frame.rms`; ignores beats. Tests: silence gives dim base; sustained loud gives the palette color; a burst rises fast and falls slowly; the hue advances over time.

## 4. Spread with tonal colors
- Spread keeps the round-robin bass / mid / high grouping. Each group draws from the same palette color index but with a tonal shift: bass group color = palette color scaled by 0.55 (deeper, darker); mid group = palette color unchanged; high group = palette color blended 0.45 toward white (lighter, brighter). All three groups advance the palette index together on bass beats so the room reads as one hue family from dark (bass) to light (highs).
- Tests: with one palette color, the three groups produce three distinct luminances ordered bass < mid < high.

## 5. Sensitivity range
- BeatDetector threshold multiplier at sensitivity 0 becomes 2.5x the rolling mean (only huge drops) and at sensitivity 1 becomes 1.08x (nearly everything); 0.5 stays 1.5x. Keep the 0.1 s debounce. Tests updated for the endpoints.

## 6. Response
- Party tick rate default 10 per second (StreamRateLimiter default 10, Settings range stays 2 to 10). Update tests that assume 8.

## Out of scope
Fully off below the gate (Phil chose dim base); per-band gates; BLE transport.

## Amendments

- 2026-09-14, Snap and Fade: one attack and one release now drive the whole room, so the settle times that used to differ per effect follow the Fade slider instead. At the shipped default that is 0.5 s everywhere: Spread (was 0.4 s), Glow's release (was 0.4 s) and the party gate's hold (was 0.3 s, now a floor rather than the value) all move to it, and Glow's 50 ms attack is what the default Snap reproduces. One attack cannot serve both kinds of effect, so the beat driven three ramp over a fifth of it (`EffectTiming.beatAttack`, floored at 5 ms): at the default that is a 10 ms crack, which lands a hit inside one tick the way Pulse, Wave and Spread behaved before the sliders existed, while Glow still breathes in over its 50 ms.
- 2026-09-14, detector re-range and a readable Snap: section 5 above is superseded. Phil reported the lights taking a few seconds to react with the marker at 69 percent. Replaying real tracks through the whole pipeline (AutoGain to BeatDetector to PartyGate to Pulse at 8 Hz) gave these low band beats per second at that marker: 1.15x gave 8.8 (dance remix) / 7.7 (hip hop mix) / 4.9 (ambient) / 5.4 (jazz); 1.35x gave 7.0 / 3.5 / 2.4 / 4.0; 1.65x gave 5.2 / 0.6 / 1.3 / 2.9; 2.0x gave 3.5 / 0.04 / 0.6 / 2.2. A dense mix keeps the bass band busy between kicks, so a kick only reaches about 1.5 to 1.6 times the rolling mean, and above ~1.65x the detector starves (the hip hop mix ran a median 4 s between pulses with gaps up to 43 s). Below ~1.2x it fires 8 or more a second and the room sits lit instead of pulsing. `BeatDetector.thresholdMultiplier(forSensitivity:)` is now a single straight line from 1.65x at sensitivity 0 to 1.2x at 1, mid 1.425x, so every marker position stays inside the usable window. Govee's raw 1.5x is no longer a named point on the curve; `minBeatEnergyThreshold` stays as the historical reference.
- 2026-09-14, Snap readout: Snap was unrelated to that lag (a Snap of 0 gives beat effects a 50 ms ramp, which lands inside one tick), but the slider did not say which way was faster, which is why Phil had it at 0. Snap now reads out the attack it asks for the way Fade does, `LabeledValueSlider.snapSeconds`, printing `instant` below `EffectTiming.shortestAttack` (about 80 percent and up) and "%.2f s" otherwise. The shared Snap and Fade caption is replaced by one caption under each slider, in the Party panel and in Settings alike.
- 2026-09-14, Wave travel speed: Wave shifted one bulb on every tick, so how fast a color crossed the room was whatever the engine's update rate happened to be (10 per second by default, 8 on Phil's machine at the time). It is now a user setting. `WaveEffect` holds a `bulbsPerSecond` inside `WaveEffect.travelRange` (1 to 15), defaulting to `WaveEffect.defaultTravelSpeed` (10), which reproduces the old behavior exactly at the shipped 10 updates a second. A fractional hop accumulator carries the leftover of a hop between ticks, so a speed that does not divide into the tick rate is honored instead of rounding back to one hop per tick; hops inside one tick are capped at one sweep of the room so an app that was paused does not come back and spin through thousands of them. A low beat still lights the first bulb on the tick it lands, whatever the speed, so the room reacts on time at 1 bulb/s; a second beat inside one hop takes the first bulb over and the earlier color is lost, which is intended. Travel is not on the `Effect` protocol: `PartyEngine` stores `waveTravelSpeed` and applies it in `start` and `setEffect` the way `timing` is applied, so leaving Wave and coming back keeps it. `GlowbeatSettings.waveTravelSpeed` persists it under `waveTravelSpeed`, clamped on load and save. The `Travel` slider (whole steps, readout "N bulbs/s") appears in the Party panel under the effect picker only while Wave is chosen, and deliberately not in Settings: it belongs to one effect.
- 2026-09-14, Fade tops out at 5 s: `EffectTiming.slowestRelease` goes 2.0 to 5.0 at Phil's request. `standardFade` is derived from `standard.release`, so the shipped default is still a 0.5 s settle; only the slider position under it moves, from about 0.46 to about 0.34. Stored `partyFade` values are slider positions on a log scale, so an old stored position now asks for a longer settle. Per the earlier ruling there is no migration code.
- 2026-09-14, Trigger Level and Always react: the row label "Reacts to" is now **Trigger Level** (Phil's name) in the Party panel, in Settings, in the marker's tooltip and in both accessibility labels, with one caption under it: "Lights kick in when the music is louder than the marker. Lower catches more, higher only the loud parts." The label column both windows share widened from 78 to `LabeledValueSlider.labelWidth` (88), because "Trigger Level" is 78.2 points in the system font and would have truncated. Code identifiers (`partyGate`, `setPartyGate`, `PartyGate`) are unchanged. Alongside it, `GlowbeatSettings.alwaysReacts` (default false, key `alwaysReacts`) is an **Always react** checkbox under the row in both windows, help text "React to every sound, no matter how quiet." While it is on: `PartyEngine` runs the gate at a threshold of 0 and hands the effect `setGate(0)`, so Glow brightens from silence; the marker's own value is kept in `PartyEngine.gateMarker` and restored the moment the box is unticked, including a drag made while it was ticked; and the beat detector is pinned to `GlowbeatSettings.alwaysReactsSensitivity` (0.5, that is 1.425x the rolling mean) rather than following the marker, because the marker also drives the detector and a grayed marker at the bottom would otherwise silently ask for the loosest detector there is and leave the room sitting lit. Ticking or unticking restarts nothing: `PartyEngine.applyReaction` retunes the gate and the detector in place. The marker and its percentage render grayed and undraggable while the box is on (`LevelMeter.isGateEnabled`, `LevelMeter.disabledOpacity`), the moving bar under them stays live.
